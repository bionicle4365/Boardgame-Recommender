# Rules

- **Infrastructure Deployment**: Never execute `terraform apply` directly. Wait for the user to execute it or use alternative CI/CD workflows as preferred by the user.

- **Task & Milestone Planning**: When the user requests planning or adding a new feature/milestone without immediate execution, create a structured GitHub Issue via `python scripts/agent_backlog.py create ...` with `owned_paths`, `forbidden_paths`, `acceptance_criteria`, `verification_commands`, plus rich `--context`, `--example` (payloads/CLI/before-after), and `--visual` (Mermaid/ASCII mockups or screenshots on the `screenshots` orphan branch), and confirm the created issue URL with the user without executing code changes.

- **Artifact Storage**: When you need to save a working script (e.g. `format_mechanics.py`) or the results of an experiment (`mechanic_frequencies.json`), save it to the `scratch/` directory. Do not save generated artifacts to your workspace or working folders.

- **Testing & Visual Proof**: Run automated unit tests (`pytest` for backend, `npm test` / `npm --prefix site_ui test` for frontend) before deploying any changes. For PRs touching `site_ui/`, capture desktop/mobile screenshots via `python scripts/capture_ui_screenshots.py` (or rely on the PR CI `ui-screenshots` job) and embed them via `--screenshot` so human reviewers can visually verify UI changes on GitHub without bloating `main`.

- **Agentic Orchestration**: For all complex workspace tasks, reference the `agentic-orchestrator` skill. Identify the appropriate specialized domains (BGG API, AWS Architecture, Site UI, Recommender System, or Data Engineering) required for the task, load their rules, and coordinate implementation sequentially (Single-Domain Plan -> Execute) or in parallel (Multi-Domain Swarm).

- **Docker Images**: Never build or push Docker images directly. Deployment processes and image builds should only be run via designated CI/CD pipelines (e.g. GitHub Actions).

- **GitHub Issues Task Queue & Completion**: Track all active and autonomous tasks as GitHub Issues via `scripts/agent_backlog.py` (`list`, `get`, `approve`, `next`, `claim`, `complete`, `block`, `review-queue`, `pr-feedback`, `submit-review`, `sync-pr-review`). Newly generated/created issues start as `agent:proposed` and require human approval (`approve <issue_number>` or relabeling to `agent:ready` on GitHub) before an autonomous agent may claim them (`agent:ready` -> `agent:in-progress` -> `agent:review` -> `agent:approved` or `agent:changes-requested` -> rework, or `agent:blocked` via `block <issue_number> --reason "..."` when stuck). Use `next --claim --worktree` (or `--checkout`) so new tasks start from fresh `origin/main` and PR rework tasks (`agent:changes-requested` or GitHub `CHANGES_REQUESTED` reviews) automatically resume `origin/agent/issue-<issue_number>` with `pr_feedback` attached. Before marking any task complete (`python scripts/agent_backlog.py complete <issue_number> --pr agent/issue-<issue_number> --push --open-pr --summary "..." --verify-report scratch/verify-<issue_number>.md --example ... --screenshot ...`), run `python scripts/verify_task.py --issue <issue_number> --report-markdown scratch/verify-<issue_number>.md` to validate branch isolation, file ownership boundaries, and required unit tests (`pytest`, `npm --prefix site_ui test`, and `terraform validate` when applicable).

- **Branch & Pull Request Isolation**: Autonomous task executors must **never** commit directly to, push to, or merge into `main` (or `master`), and must never merge Pull Requests. All autonomous task work must happen on an isolated `agent/issue-<issue_number>` branch and be submitted as a Pull Request to `main` via `python scripts/agent_backlog.py complete <issue_number> --pr agent/issue-<issue_number> --push --open-pr --summary "..."` so the human reviewer performs the final merge.
